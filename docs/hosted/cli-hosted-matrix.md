# Native CLI to hosted tool matrix

`cli-hosted-matrix.json` is generated by `go run ./cmd/hosted-parity` from the
live Kong command schema and executable hosted tool catalog. Regenerate it after
catalog changes and check it with `go run ./cmd/hosted-parity --check
docs/hosted/cli-hosted-matrix.json`.

The current baseline covers 360 visible native leaves in the 11 active services
and 233 active hosted tools (271 total). It maps 233 hosted tools across 243
native leaves because Search Console exposes `query` and the equivalent
`searchanalytics query` leaf, and Docs has equivalent `list-tabs` / `tabs list`
leaves plus the reviewed `named-range list` hyphen bridge to
`docs_named_range_list`. Forms question add/move/delete each have equivalent
direct and grouped command leaves mapped to one tool. Docs tab add/rename/delete
also map direct and grouped aliases. Counts are: 243 implemented/unverified hosted
leaves, 70 reviewed eligible missing, 39 requiring resource/transport/billing
implementation design, 2 explicitly excluded, 1 outside the current scope
boundary, and 5 deferred. Forms `raw` is a fixed GET variant of `forms_get`,
not a separate missing hosted tool.

`implemented_hosted_unverified` means only that an executable fixed-schema
hosted binding exists. Every `live_verified` value is false; fixture success and
catalogue presence are not live Google verification. Every remaining non-deferred native operation now has an `engineering_review`
record in this matrix. Future unknown commands are `unreviewed_mapping`, never
assumed eligible merely because their service uses audit-free OAuth. The old
`missing_requires_audit` label meant an internal engineering review—not a paid
Google security assessment—and is no longer emitted. Empty binding methods have `http_methods_known: false`.

Calendar and Drive Labels are deferred and are excluded from active gap counts.
The matrix includes the integrated Sheets and Apps Script runtime batches;
regenerate it whenever executable bindings change.

A mapped command means an executable fixed-schema binding exists; it does not
claim full native CLI flag/variant parity. Missing methods, resource models or
transitive-scope/billing checks must still receive engineering review before adding an adapter.

## Per-tool live-verification inventory (#97)

Generate `live-tool-matrix.json` with:

```sh
go run ./cmd/hosted-parity --live-matrix --evidence docs/hosted/live-tool-evidence.json > docs/hosted/live-tool-matrix.json
go run ./cmd/hosted-parity --live-matrix --evidence docs/hosted/live-tool-evidence.json --check docs/hosted/live-tool-matrix.json
```

This mode reads the executable catalogue, read-only binding metadata and curated
`live-tool-evidence.json`; it does not run a native schema subprocess, contact
Google/providers, or access credentials. Every candidate remains
`implemented_unverified_live`. Exactly two existing-deployment GA4 representative
variants currently have attributable allow/deny evidence; neither whole-service
coverage nor deployed-candidate acceptance is inferred. Unknown source SHA stays
`null`. Add proof only after genuine exact-operation acceptance, never from a
fixture pass or another tool. Scope alternatives and destructive flags are static
binding metadata; absent method declarations and argument-specific destructive
behavior are explicitly not invented.


## Complete remaining-capability scope review (19 October 2026)

The canonical evidence is `cmd/hosted-parity/capability-review.json`, embedded by
the generator and checked against the actual Kong command schema, native Run
receivers, approved scope catalogue and saved official method/scope evidence.
It reviews all **164** previously unmapped, non-deferred leaves at source
`288ba8a3741958150f1b4df78518cd4143c7712c`; one Forms read alias, four Docs range/named-range operations and five Docs text-edit leaves are now mapped,
leaving **154** currently unmapped, explicitly classified rows. No row is silently treated as a paid
assessment requirement.

**153 reviewed rows have an approved-scope variant with no paid assessment
barrier identified.** At the original review snapshot, 121 were
fixed-adapter candidates (nine Docs operations are now implemented), 30 need resource/transport/billing design, one remains
excluded by owner policy, and one is the already-covered Forms alias. Nine further
Connected Sheets rows require additional `bigquery.readonly` authorization, not
currently in the hosted allowlist; no paid-assessment classification is assumed.
Together there are 39 design gaps. The two outside-boundary cases are Drive Activity and native shared-drive enumeration;
no unsupported conclusion about paid assessment exemptions is made for them.

Commands named `raw` are classified by their source, not their name. The native
Docs/Slides/Sheets/Drive raw commands use fixed single-resource GET endpoints;
bounded selected-file projections are eligible, not arbitrary HTTP proxies.
Forms raw returns the same Form resource as the existing typed `forms_get`.
Arbitrary Sheets request batches remain excluded as raw input; typed allowlisted
batch variants would need their own engineering design. Selected-file sharing
and user-permission audits are eligible: native `--file` does not impersonate the
user argument or scan a tree. Folder sync needs trusted staged/local-client files
and child-grant planning, not arbitrary shared runner filesystem access.

BigQuery has a useful native bounded dry-run variant; actual query execution
still needs referenced-project authority, explicit billable approval, safe SQL
semantics and bounded result collection. Native local-file outputs and Forms
Pub/Sub watches need product/runtime/customer-infrastructure design, not a
blanket paid Google assessment. All future adapters still require their own
permission, scope, payload, tenant, retry and real-acceptance checks.


Connected Sheets is an explicit additional-scope exception: the official
[guide](https://developers.google.com/workspace/sheets/api/guides/connected-sheets)
requires `bigquery.readonly` for BigQuery Connected Sheets data, beyond ordinary
Sheets method scopes. All nine native variants are design-required until explicit
optional authorization is assessed; refresh/update/add also need customer billing
controls. They are not included in the 153 proven-approved-scope rows and are not
assumed to require paid Google security assessment. No consent scope was added.


This census covers the existing native CLI engine, not every operation in the
underlying Google APIs. Fully mapped CLI services are not claimed to have full
Google API coverage. API-only methods and batch request types absent from the
native command tree remain a separate discovery pass, not implicitly excluded
as requiring paid assessments.

## Docs structural/table batch

Eighteen existing eligible native leaves now have fixed-schema hosted adapters:
header/footer create/delete, footnote, horizontal/page/section breaks, blank-table
insertion, person/date chips, table row/column insert/delete, merge/unmerge and
pinned headers. Inputs are inline, bounded and delegated to native validators;
local files, stdin and persisted batches are not exposed. Existing placement,
table and revision checks are retained (not every native operation has a revision
precondition). Each invocation requires its exact tool and selected-document
write grants; row/column/segment deletion additionally requires destructive
permission. Chat uses the existing exact-argument one-use write approval path.
All new adapters disable uncertain-write retries. Signed-runner fixtures prove
request shapes, selected-file/tool/scope denials, destructive denials and no
replay after a simulated 503. These are not live Google acceptance results.

## Shared Docs/Drive comment lifecycle

Fourteen existing eligible operations now delegate to native comment handlers:
Docs add/delete/get/list/locate/reply/resolve/reopen and Drive
create/update/delete/reply/resolve/reopen. Exact selected-file/tool grants and
existing drive.file scope are required, including for Docs comments. Writes
retain one-use chat approval policy; deletion requires destructive authority.
No raw anchor JSON, arbitrary requests, files/stdin, impersonation or all-pages
option is exposed. Locate reads only the selected comment and document, with
host/path pairing enforced across the two APIs. Mutations are single-attempt.
Signed-runner fixtures prove all fourteen operations and authorization/HTTP
boundaries, including no replay after uncertain writes. Live verification remains
outstanding; these new tools are not in the integrated chat starter allowlist.
